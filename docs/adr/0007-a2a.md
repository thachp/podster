## Context

[A2A 1.0](https://a2a-protocol.org/latest/specification/) assumes a client hands work to a server agent, which runs it. Podster runs nothing: it records a shared task that independent agents accept, discuss and deliver. So A2A has to map onto Podster in both directions without changing who decides anything:

- **Inbound,** an agent's own A2A client calls Podster to read its tasks, post to threads and, through the extension, accept or submit.
- **Outbound,** Podster offers a task to an agent that registered an A2A endpoint, and reads back what the agent reports.

Rust decides authority on every path ([ARCHITECTURE](../spec/ARCHITECTURE.md#a2a-adapter)). The gateway authenticates and translates, as it does for MCP. A2A content is data, never instructions.

## Decision

### The gateway's A2A surface

- **Where:** `POST /a2a` on the gateway, with the card at `/.well-known/agent-card.json`. New code goes in `apps/gateway/src/a2a/`.
- **The SDK's transport, with Podster's own handler.** The gateway uses `@a2a-js/sdk`'s `JsonRpcTransportHandler`, `validateVersion` and error classes, which run on Workers with `nodejs_compat`. It implements `A2ARequestHandler` itself. It does **not** use the SDK's `DefaultRequestHandler`, which runs an executor and keeps its own task store, so it would make Podster run work and hold a second copy of tasks.
- **Each operation is one Podster read or command** through the same internal API calls as MCP capabilities, so `crates/policy` and `crates/core` decide.
- **Before the handler, in this order:**
  1. The gateway's per-client limit, which every request passes.
  2. The method, `Content-Type`, and the body size of at most 64 KB, with the body read once. Then `A2A-Version`: a missing header is read as 0.3 and refused with `VersionNotSupportedError` (spec 3.6.2), and both SDK clients send `1.0` themselves. A patch of 1.0, such as `1.0.1`, is served as 1.0, since patch numbers never count in negotiation (spec 3.6, decision 192). Major and minor are read strictly, digits only, and anything else is refused. None of these reveals anything, so they come before authentication, as the step 7 review asked.
  3. Authentication (spec 7.4), by the `/a2a` resource server.
  4. The agent's rate limit. It's the same bucket as MCP, keyed on the same `externalId` (`mcp:${externalId}` today), so A2A and MCP together get one agent's allowance (decision 123).
  5. Parsing. Streaming methods are refused here, before the handler runs, so no response is ever held open, and a method the profile doesn't name gets `-32601`.
- **The card** lists one JSON-RPC 1.0 interface, has streaming, push and the extended card off, and declares an `oauth2SecurityScheme` with an authorization-code flow, PKCE and scope `a2a`. It describes Podster only: no rooms, tasks or agents. It says "preview" until the owner calls the gate.
- **The profile** is `docs/spec/A2A-PROFILE.md`: operations, state mapping, errors, the extension, limits, and decision 141's kit exceptions. A gateway test checks the card names only the operations the profile lists.

### Authentication: one authorization server, two resources

Spike B showed the gateway's combined `OAuthProvider` takes one resource, so every route it protects shares one audience. Step 7 changes it, as its own PR with decision 127's deeper pass:

- **One `OAuthAuthorizationServer`, with resources `/mcp` and `/a2a`,** each hosted by its own `OAuthResourceServer` in the same Worker. Every token is bound to exactly one resource. A token for one is refused at the other.
- **`defaultResource` and `legacyGrantResource` are `/mcp`.** With two resources, a request that omits `resource` is otherwise refused, which would break today's MCP clients that don't send it. Grants stored before the change are meant to stay MCP. That rests on the package's documentation: spike B couldn't make a grant with no stored resource to test it.
- **Each resource server checks its own scope.** The package advertises `requiredScopes` but leaves enforcing them to the handler, and the gateway's MCP handler doesn't check scope itself today. So the `/mcp` handler refuses a token without `mcp`, and the `/a2a` handler a token without `a2a`, with `insufficientScope`.
- **Consent grants `a2a` for an `/a2a` request, and `mcp` for an `/mcp` one,** never both on one token, and says on screen that the agent will act over A2A. Today the consent code refuses anything but `mcp` and `offline_access`.
- **Replacing a grant is per resource.** Today `approveConsent` revokes every grant with the same `externalId`, which is one person, OAuth client and organization. Unchanged, consenting to `/a2a` would end that client's live `/mcp` grant. So a new consent replaces only that client's earlier grant for the same resource.
- **The same identity.**
  - **The same OAuth client** consenting to both resources gets the same `externalId`, so `resolveAgent` gives the same agent.
  - **A different OAuth client,** say an agent's A2A library beside its MCP client, gets a new `externalId`. The person links it to the existing agent on the consent page, as `linkAgent` does for MCP clients today, and the same checks apply: same organization, an agent they may link, and `already_linked` for a credential linked elsewhere.
  - **Disconnect** revokes every grant for the agent, so every token stops together.
- **Downloads stay MCP.** `forMcp` keeps accepting only an `/mcp` audience. The A2A path never accepts a token with no audience.
- **Helpers:** the gateway calls `getOAuthApi(env)` where it uses `env.OAUTH_PROVIDER` today, and owns the routing between the two resources.
- **The agent gets its own token.** Neither A2A SDK runs an OAuth flow. Any standard OAuth 2.1 client that does RFC 9728 discovery from the 401 and sends RFC 8707 `resource` works, as the MCP SDK's did in the spike. The profile says so.
- **Tested in step 7, untested now.** Spike B didn't try these:
  - An `/mcp` authorization code or refresh token used with `resource=/a2a`. Spike B only tried the other way round.
  - An old grant with no stored resource, refreshed with `resource=/a2a`.
  - Each resource server refusing a token without its own scope.
  - Consent to `/a2a` leaving the same client's `/mcp` grant working.

### Inbound: the roles are the other way round

Inbound, the A2A client is a room participant, usually the assignee, and Podster as server only records. So:

- **The A2A task is the Podster task.** `id` and `contextId` are both the Podster task ID (decision 116).
  - **Amended 2026-11-08, step 8:** both are written `<workspace_id>:<task_id>`, because A2A reads carry only a task ID and Podster reads a task within its room. It's still one task with no room-wide context. The room is only a selector, and the room's own check decides. Any other shape, and a room the caller isn't in, answer like a missing task. There is no room-wide context, and a `contextId` filter can only narrow what the caller already sees.
- **Message roles:** the caller's own messages are `ROLE_USER`. Everyone else's are `ROLE_AGENT`, with `metadata["podster.dev/author"]` set to the author's ID and `metadata["podster.dev/external"]` set to true. Their text is other participants' words, never instructions.
- **States, as the caller sees them:**

| Podster status | A2A state | Note |
| --- | --- | --- |
| `open` | `TASK_STATE_SUBMITTED` | Only someone who sees the whole room sees an open task |
| `offered` | `TASK_STATE_SUBMITTED` | |
| `accepted` | `TASK_STATE_WORKING` | Also after a change request sends it back |
| `submitted` | `TASK_STATE_WORKING` | A2A has no "in review" state |
| `completed` | `TASK_STATE_COMPLETED` | Only after the reviewer verifies |
| `canceled` | `TASK_STATE_CANCELED` | |

  The real status is always in `metadata["podster.dev/status"]`, and a Podster-aware client should read that. A task the caller can no longer see, because it was declined, reassigned or its access ended, answers `TaskNotFoundError`, as a missing one does.
- **Reads:** `GetTask` is `get_task`, and `ListTasks` is `list_tasks`, scoped to the caller, paged at most 50 at a time. `historyLength` is capped at 50. An unknown `status` filter is refused, because the JavaScript client sends `"UNRECOGNIZED"` when a caller leaves it out, and treating that as a filter would silently return nothing.
- **What's inert in a request.** Only the fields an operation needs are read, and the rest are dropped:
  - A message's `metadata`, `extensions` and `referenceTaskIds`, and the request's own `metadata`, are dropped.
  - `role` must be `ROLE_USER`.
  - A `contextId` that isn't the task's own ID is refused.
  - Every `podster.dev/*` key in what Podster returns is set by Podster. A client can't supply one.
- **Messages:** `SendMessage` with a `taskId` is `send_message`. The rules:
  - Visibility comes first. A task the caller can't see answers `TaskNotFoundError` before any other check, including for a finished task.
  - The idempotency key is `a2a-msg:<messageId>`. The API scopes each key to its caller, by `actor_id`, in the task's room, and the request hash covers the task ID and the text, so a retry posts once, and a reused `messageId` with a different task or text in that room is refused. The lifecycle extension's keys are `a2a-lc:<requestId>`, so neither collides with the other or with MCP's.
  - Text parts only, at most 8, and 16 KB in all (decision 123). URL and inline parts are refused for now. Step 14 turns a URL into an external link (decision 121).
  - A message with no `taskId` is refused with `UnsupportedOperationError` (decision 115).
  - A message to a finished task is refused by Rust, and the gateway only translates the refusal to `UnsupportedOperationError` (spec 3.1.1). Today `handle_send_message` lets MCP post to a finished task, so step 9 adds a rule in `crates/core`: a message that arrives over A2A, which the gateway marks as its origin, is refused once the task is terminal. MCP is unchanged.
  - `returnImmediately` changes nothing, because Podster never waits on work.
  - Text never changes a task, whatever it says (AC-18).
- **Cancel:** `CancelTask` answers `TaskNotCancelableError` for any task the caller can see, and `TaskNotFoundError` for one it can't. Cancelling belongs to the requester or an admin, through Podster's own commands, and the extension doesn't add it. This is the one cancel error the spike left open. It also matches what the kit expects for finished tasks, read from its source (`CORE-CANCEL-002`), not from a run.
- **Unsupported operations** get their named errors: `UnsupportedOperationError` for streaming and subscribing, `PushNotificationNotSupportedError` for all four push operations, and `UnsupportedOperationError` for the extended card. The card declares none, so spec 3.3.4 calls for that, not `ExtendedAgentCardNotConfiguredError`, which the kit's `CORE-CAP-003` checks.

### Inbound lifecycle: the Podster extension

Plain A2A has no accept or submit, and a message's text must never become a command (decision 113). So:

- **An extension** `https://podster.dev/a2a/lifecycle/v1`, declared on the card, not required, and activated by the client in `A2A-Extensions`.
- **It adds four methods:** accept, decline, release and submit. Each carries the task ID, the task `version` and an idempotency key, prefixed `a2a-lc:` with the hash covering the task ID, and submit also carries artifacts (links in M3, files from step 14). Each becomes the existing capability, so policy and the state machine decide exactly as for MCP.
- **Without it,** a client can still read and post messages.

The method names and their parameters are settled in review, as below.

### Outbound: offers to a registered endpoint

- **Registering.** An agent, or its organization's admin, sets one endpoint (decision 119) on the agent's `Principal`. It's checked against the egress rules when it's set and again before each send. Registering grants nothing in any room. Each registration has a version that goes up whenever the URL changes, including setting one after a delete, and never goes back.
- **The credential** (decision 122):
  - **Signing.** Each request is signed as wake's are: HMAC-SHA256 over `{t}.{body}`, where the body is the exact JSON-RPC body sent, in `X-Podster-Signature`. The key is a per-endpoint secret made at registration and shown once, as wake's is.
  - **The bearer token** is optional. It's encrypted with a key from a Worker secret, which the owner sets in that session. It's write-only: never returned in a read, an event, the inbox or a log.
  - **Clearing.** The token is cleared when the URL changes, when the endpoint is deleted, and when the agent is disconnected or revoked.
  - **The signing secret follows the same rule.** A URL change makes a new secret, shown once, and the old one stops signing at once. Deleting the endpoint, disconnecting or revoking deletes it. Setting the same URL with `rotate_secret` makes a new secret without moving the version, so a lost secret needs no delete.
  - **The key.** `A2A_TOKEN_KEY` is 64 hex characters. A value that isn't fails closed as unset: endpoints can still be set, a token can't (503 `token_storage_unavailable`), and the API logs `a2a.token_key_invalid` with nothing of the value. Changing the key leaves stored tokens unopenable, so those endpoints send nothing until a token is set again.
  - **The linking person leaving.** Claim checks only the agent's `Principal` status, and when the person who linked the agent's credential leaves its organization, the gateway refuses that credential (`credential_owner_left`) while the `Principal` stays active. Wake has the same gap. So step 12's send-time recheck must also refuse when the agent's linker has left, and that's built with step 12:
    - Each set records who set the endpoint. For an agent, that's the person who linked the credential it came with, and when, which the gateway adds to the agent's assertion as `linker`. For an admin, it's the admin, from the start of their current membership. A set with neither is refused.
    - Before each send, the agent's `Principal` asks that person's own `Principal` whether they've left the agent's organization since then. The gateway already pushes every departure there, from its departure outbox, and the person's `Principal` now keeps a permanent `org_left` record of each one, since the room sweep's own record is dropped after about 30 days.
    - If they've left, nothing is sent, and the endpoint is deleted, with its secret and token. If the answer is unavailable, nothing is sent and the job is retried. The gateway's D1 is never read for this, because it's another service's read model.
    - An endpoint set before step 12, with nobody recorded, sends nothing until it's set again.
  - **Removal from a room leaves the endpoint.** It belongs to the agent, not to any room, and only disconnecting clears it. Step 12's consumer rechecks the agent's access to the task's room at send time, so an agent removed from a room gets nothing from it.
  - **Rotation:** setting a new token replaces the old one. A rotation path that keeps sends working while both are valid is owed before production.
- **Sending.** When a task is offered to an agent with an endpoint, the outbox puts a job on the A2A queue holding IDs only: the task and the offer attempt. The consumer in `apps/api` then:
  - records the endpoint URL and registration version on the attempt;
  - rechecks that the task is still offered to that agent, the agent is still active (below), and the endpoint still passes the egress rules;
  - reads the title, instructions and criteria;
  - sends `SendMessage` with `returnImmediately`, a timeout, `redirect: "manual"`, the signed request, and the bearer token if one is stored.
  The message's `messageId` is the offer attempt's ID, and its parts are the text and a Podster link. A task that moved on while queued sends nothing.
- **As built in step 12:**
  - **Recording the attempt.** An attempt is recorded in the offer's own transaction, for an agent assignee other than the actor, keyed to the offer's `task.offered` event. The room's outbox is the attempt row until it's queued, so a failed queue send waits with its own backoff.
  - **The job** is `{ ws, attempt, agent }`.
  - **The consumer's order:**
    1. the agent's `Principal`: connected, endpoint on, egress, setter still present, and the token opened;
    2. the room, as that agent with that generation: participant, fence, the task visible to it, the room not archived, and the task still offered to it on the attempt's offer;
    3. the room returns the text;
    4. the send, with a 60-second lease so a second delivery waits;
    5. the report to the `Principal`;
    6. the room records the outcome.
  - **The body is one text part,** with the link in the text, and the A2A task ID `<room>:<task>` and the attempt ID as message metadata.
  - **What counts as an answer.** Only a 2xx with `result.task.id` that passes the remote ID check, or with `result.message` and no task, counts as answered. Anything else counts as a failure toward switching the endpoint off, and the queue retries the same message: a redirect, a timeout, a JSON-RPC error, an answer over 64 KB, an invalid ID, or an empty result.
  - **Retries.** After five, the job goes to the dead-letter queue, which logs its IDs and acknowledges it.
- **Duplicates.** A remote agent may not remove duplicates. Spike C's SDK server made a second task for a resent `messageId`, which spec 3.3.1 allows. So:
  - Podster keys every send on its own attempt record, and a redelivered job for an attempt that already got an answer sends nothing.
  - **Podster tracks only the remote task it got an answer for.** It stores that remote task's ID on the attempt, reads only that ID, and ignores any update or ID it didn't record.
  - **A remote task ID is checked before it's stored or logged:** at most 256 bytes of printable ASCII with no whitespace. Anything else counts as a failed send.
  - A send that times out after the remote received it, then retried, can leave an extra task on the remote side that Podster never learns about. Podster can't cancel that one. The profile says so.
- **Reading back.** Each `GetTask` is its own queued job with a delay that backs off from 1 minute to 1 hour, and reading stops at a terminal state or after 7 days (decision 117). A redelivered read is skipped by its number.
- **As built in step 13:**
  - **Who queues a read.** The room's alarm queues each read once it's due, so the room alone decides whether to read. The job is `{ ws, attempt, agent, kind: "read", read: n }`, IDs only. The queue's own delay isn't used. A read the endpoint didn't answer usably isn't retried by the queue: the room schedules the next one. Only an internal error, such as the room being unreachable, is retried by the queue. A read queued but not back in 30 minutes is queued again with the same number.
  - **Each read rechecks:** the agent's `Principal` claim, as for a send; then the room, as that agent with that generation; then that the endpoint's URL and version are still the ones pinned.
  - **The answer.** `GetTask` asks for `historyLength: 0`. Its answer is parsed under decision 123's caps, and anything over a cap refuses the whole answer as a failed read: more than 8 parts, more than 10 artifacts, more than 16 KB of text, more than 64 KB in all, or an invalid ID. What's kept is data: the status message's text, the artifacts' text as a note, and their URL parts as links labelled by file name or artifact name.
  - **The effect.** It runs in the read's own transaction as the agent's command, through policy and then `decide`. If its command is refused, the read is applied again without it, so the read still counts. A refused submission is held instead.
  - **Origin.** Events and audit rows it makes carry `origin = 'a2a_remote'` and the attempt's ID. The audit row's `actor_kind` stays `agent`.
  - **The held response** is stored in `a2a_held`, and the requester is told with a `task.a2a_response_held` event. Its links pass the same check as a submission's first. Any that fail are dropped and counted, and a response with none left is held without links.
  - **The archive guard.** Each effect runs the same pre-command guard as every room command, inside the read's transaction, so archiving during a `GetTask` stops the effect. The read is recorded, and reading ends.
  - **A message the endpoint reported** carries `origin = 'a2a_remote'` on the message row. Reads show it as `origin`, and A2A shows it as `podster.dev/origin`. If the status message's text is over 16 KB, the thread gets a fixed note in its place. That isn't a failed read. A remote `CANCELED` is recorded as `task.a2a_remote_canceled`, and a reported failure under review as `task.a2a_remote_failed`.
  - **Cancel out.** Canceling a task marks each sent attempt that's still being read, and reading for it ends. The alarm then queues a cancel job, and `CancelTask` goes out once. `TaskNotCancelableError` (`-32002`) is recorded and not retried. A failed send is retried by the queue.
- **As built in step 13b, `request_changes` out** (decision 114). There's no second path. It's an attempt with `kind = 'change_request'`, through step 12's queue, claim, begin, send, finish and dead-letter handling, and step 13's reading:
  - **When one is recorded.** In the request-changes transaction, an attempt is recorded only if the task goes back to the agent, who is still here and isn't the one asking, and the task's latest `task.submitted` event has `origin = 'a2a_remote'`. Its `origin_ref` names the attempt whose remote task completed the submission. That remote task and its `contextId`, kept at send time once it passes the remote ID check, become the new attempt's references.
  - **When it sends.** `podster_core::a2a::may_send_kind` sends a change request only while the task is accepted, with that agent, on that change request. A change request is current only while it's the latest, and no `task.offered`, `task.accepted`, `task.released` or `task.submitted` came after it (`current_change_request`). So a release followed by a new offer and acceptance supersedes it, even with the same agent. A superseded attempt ends as `superseded` without sending. If it was already sent, reading ends and nothing it reports applies.
  - **What `begin` reads,** at send time: the reason, from the change request's own event, and the submission number.
  - **The body** is `SendMessage` with `referenceTaskIds: [<completed remote task>]`, the same `contextId`, and the attempt's ID as `messageId`. It carries the text from `change_request_text`, with `returnImmediately`.
  - **Reading back:** the task now on that change request counts as the attempt's own, so `COMPLETED` submits the next submission and `FAILED` releases the task.
- **Read-back is pinned to the endpoint.** Before each read, the consumer compares the attempt's stored URL and registration version with the endpoint's current ones. If they differ, because the endpoint was re-pointed, deleted or switched off, it stops reading that attempt for good. A re-pointed endpoint can't answer `WORKING` or `COMPLETED` for a task it never got, and the old token was already cleared, so it never reaches the new URL.
- **Every follow-up has the same checks.** `GetTask`, outbound `CancelTask` and the new task a change request sends are each:
  - an IDs-only job;
  - rechecked for access and an active agent;
  - checked against the egress rules and the pinned endpoint;
  - read for content, where they carry any, only at send time.
- **What Podster reads back is bounded.** A remote response over 64 KB is refused unread past that point and counts as a failed read. Only the fields Podster uses are kept.
- **Mapping.** A new pure module, `crates/core/src/a2a.rs`, decides what each remote state means given what Podster has already recorded. A2A state decides nothing on its own:

| Remote state | Before the agent accepted | After it accepted |
| --- | --- | --- |
| `SUBMITTED` | Nothing | Nothing |
| `WORKING` | `accept_task`, as the agent's own act (decision 112) | Nothing |
| `INPUT_REQUIRED` | A thread message | A thread message |
| `COMPLETED` | Held as an unaccepted response, flagged to the requester | `submit_task`. Never `verify_task` |
| `REJECTED` | `decline_task` | `release_task`, since `decline_task` only applies to an offer |
| `FAILED` | `decline_task` | `release_task` |
| `CANCELED` | Recorded, and Podster stays authoritative | Recorded, and Podster stays authoritative |
| `AUTH_REQUIRED` | A thread message that grants nothing (spec 7.6.4) | Same |
| Anything else | Ignored | Ignored |

  A late update after a decline, cancel, revocation or reassignment changes nothing, because each effect still goes through policy against current state.
- **The fence on remote-state effects.** `accept_task`, `submit_task`, `decline_task`, `release_task` and thread messages that come from a remote state run in the API's consumer, with no gateway assertion and so no `gen`. So before calling the room, the consumer:
  - reads the agent's current connection generation from its `Principal`, and checks `Principal.active(gen)` as every command does under the [disconnect fence](../spec/ARCHITECTURE.md#global-disconnect-fence);
  - passes that `gen` to the room, which applies its `principal_fence` floor as for any command;
  - records the command's origin as `a2a_remote`, with the attempt's ID, in the event and the audit log.
  Disconnect and revocation delete the endpoint and its token, and stop every attempt's sends and reads. A job that runs after them is refused by the recheck. This is what AC-27 (a queued job after revocation) and AC-29 (a disconnect racing a command) test for this path.
- **Remote content into Podster.** It's always marked `external`, never instructions:
  - **Decision 123's caps apply to what comes back as well:** at most 10 artifacts, and at most 8 parts in each artifact or message. A response past either is refused, not cut, and counts as a failed read.
  - **`COMPLETED`'s artifacts become a submission's links,** under decision 123's limit of 10. A text part becomes the submission note, refused past 16 KB rather than cut. URL parts are kept as external links (decision 121), and inline bytes and data parts are dropped. If nothing usable is left, the response is held and flagged as for one before acceptance.
  - **A server that finishes before answering** ([decision 174](../spec/PRODUCT.md#decisions-needed)). A server may ignore `returnImmediately`, as LangGraph's does.
    - A `SendMessage` answer that already carries a task in a terminal state is applied as read 0, right after the send is recorded and before any read: the same caps, `decide_remote` and `a2a_remote` origin as a `GetTask` answer.
      - **The claim first.** The send can take up to 10 s, so the consumer claims the agent and its endpoint again first. Only if the agent is still connected, its endpoint's setter is still in its organization, and the URL and version are unchanged is read 0 applied, or its history fetched.
      - **What's still open after the claim.** A window of up to 10 s stays between that claim and the apply, while the history follow-up runs. In it, the room still rechecks against its own state: the agent's membership and fence, the archive, and whether the task is still on this attempt's offer. It doesn't recheck the endpoint or the setter.
      - **Once only.** The room takes read 0 once, for a sent attempt with no read queued or applied. A redelivered send job finds the attempt sent and applies nothing, and if applying it fails, the reads that follow see the same task.
    - **When the agent accepts,** through MCP or A2A as any accept is made, a response held for the task's current offer is submitted as the agent, marked `a2a_remote` with the attempt's ID.
      - **The endpoint must still be the same.** The room first asks the agent's `Principal` for the endpoint's URL and version, which carry no secret. Only if it's still active and enabled at the URL and version the response came from does the submit run.
      - **Its setter must still be in the organization.** The same check a claim makes: whoever set the endpoint must still be in the agent's organization. If they've left, or that can't be told, or the `Principal` can't answer, nothing is submitted. Deleting a departed setter's registration is left to the next claim, which does it.
      - **Its own transaction.** The submit commits straight after the accept, in a transaction that rechecks the agent's access, the archive and the task. It consumes the held row as it submits. Any failure, a 5xx included, rolls back only the submit, so the accept stands and the hold stays.
      - **The accept's answer** is its own, so a replay answers the same and submits nothing more.
      - **What's never submitted:** a response held for an earlier offer, or from a change request.
    - A `COMPLETED` with no artifacts, from a read or a send answer, gets one more `GetTask` with `historyLength` 1. The last `ROLE_AGENT` message's text becomes the note and its URL parts the links, under the same caps. It's made only when the read names the remote task Podster recorded, and its answer must name it too. A failure, a cap or nothing usable leaves the read as it was, so a hold stands. This request doesn't count toward the endpoint's failures.
  - **`INPUT_REQUIRED`'s and `AUTH_REQUIRED`'s status message** becomes one thread message, text parts only, at most 8 parts and 16 KB at most. Longer text is refused, and the thread gets a note that a message was too long.
- **Changes after completion** go out as a new A2A task with `referenceTaskIds` and the same `contextId` (decision 114). **Cancel** goes out as `CancelTask`. If the remote task is already finished and refuses, that's recorded and not retried.
- **Egress** is `crates/egress`'s wake rules: `https`, a public DNS name, no IP address in any form, no credentials, the default port, not `podster.dev`, `global_fetch_strictly_public`, and no redirects (decision 134).
- **Failures.** Three failed requests in a row to the endpoint switch it off, as wake's do, and setting it again turns it back on. Sends and reads both count:
  - a timeout or HTTP error;
  - a redirect;
  - a response over 64 KB;
  - a remote task ID that fails its check;
  - a response that isn't valid JSON-RPC.
  Any success resets the count. The offer stays in Podster for the agent to see over MCP or the inbox. This is proposed, like the rest of this ADR.

### Files

Inbound, files come only through `create_upload` and are named on submit (decision 121). Outbound, input files are Podster links that need the agent's own authorization, never bytes or a public URL. A file reference a remote agent sends is kept as an external link and never fetched.

As built in step 14:
- **`SubmitTask` takes `files: [{ id, label? }]`,** mapped to `submit_task`'s `files`. The API's file rules decide them, and a file refusal is named, never shown as a missing task.
- **Inbound URL parts** become a `Link from the client: <url>` line, after the same check as a submission's links. `raw` and data parts are refused.
- **An offer** lists the task's input files that the agent can see now, within a 4 KB share of the offer: each ready file as `- <link> "<name>" (<id>)`, and each one still scanning as `- not ready yet: "<name>" (<id>)`.
  - The link comes first, so a name can't pose as one. A name has control characters, line separators and bidi controls replaced, and is cut to 120 characters.
  - Blocked, failed and removed files aren't named.
  - The link is `GATEWAY_URL + /a2a/files/<room>/<file>`, a download route under the A2A resource. The offer says to open it with the agent's `/a2a` OAuth token, and to send that only to the gateway's host.
  - **The route takes only an `/a2a`-audience token** with the `a2a` scope. An `/mcp` token, a legacy token with no audience, or an Agent Auth JWT counts as no credential there. `/v1/files` still refuses an `/a2a` token, so #157's audience separation holds both ways.
  - The gateway asks the API for the same `/v1/files/<room>/<file>` as the agent, so the file and visibility checks are the API's, on every download. It passes only the API's file headers, and only for an attachment with `nosniff`.
- **Read back,** a status message's URL parts become `Link from the agent: <url>` lines, and any that fail the check are dropped.

### What stays the same

MCP and Agent Auth are unchanged, apart from the authorization server's construction in step 7. Inbox events stay ID-only. Wake keeps working beside an endpoint. Logs carry IDs only: no message bodies, task text, URIs, endpoints or tokens.

## Spike results

All three ran locally on 2026-11-08 UTC. Each folder's README has the details.

- **A, inbound** (`spikes/m3-a2a-inbound`):
  - 14 tests in workerd passed.
  - The project's JavaScript client passed 8 of 8 checks and its Python client 6 of 6, both unpatched.
  - Local time was about 3 ms at p50. The Worker was 21 KiB gzipped.
  - **Found:** roles are reversed inbound, A2A has no review state, the JavaScript client sends `"UNRECOGNIZED"` for an unset `status`, and cancel needs one error.
- **B, the audience** (`spikes/m3-a2a-audience`):
  - 9 tests in workerd passed, each a full flow with PKCE.
  - A standard OAuth client followed by the A2A client passed 10 of 10.
  - **Found:** the split described above is needed, with `defaultResource` set.
- **C, outbound** (`spikes/m3-a2a-outbound`), the local half only:
  - 10 tests in workerd passed through a local queue, against the project's own SDK server.
  - **Found:** duplicate remote tasks from a resent `messageId`.

**What didn't run:**

- **The compatibility kit didn't run in the spikes,** because the session permission check refused running its code (decision 142). It ran at M3's gate, on 2026-11-10, locally and on staging. The A2A profile has the results.
- **An independent implementation in either direction.** LangGraph's server installed, but starting it was refused by the permission check.
- **Anything on a deployment.**

## Consequences

- **Agents that already use A2A can read and talk on their Podster tasks unchanged, but they need the extension to accept or submit,** unless they're reached outbound. Podster then reads their `WORKING` and `COMPLETED`.
- **Step 7 is a larger change to `apps/gateway/src/index.ts`** than a new route: it changes how every OAuth token is issued and checked, so it carries a deeper security pass and its own PR.
- **A2A clients can't tell "in review" from "working"** without reading `podster.dev/status`.
- **Outbound offers are the first place task text leaves Podster to an address an agent chose.** It's read at send time, under the egress rules, and only for an agent the task is offered to.
- **Podster can leave an orphan task on a remote agent** after a timed-out send. It can't see or cancel that task.
- **Remote-state commands carry the same fence as any other,** at the cost of one `Principal` read per effect.
- **Support isn't claimed** until the owner calls the gate (decision 132). The kit and LangGraph have run, and the profile and M3's plan list what's still open. **2026-11-11:** the owner called the gate met, accepting local runs for four items that didn't run on staging ([decision 193](../spec/PRODUCT.md#decisions-needed)). The card and docs still say "preview", and whether that changes is a separate question for the owner.

## Proposed details to settle in review

- **The extension:** method names and parameters, and the error for a call without it activated.
- **The outbound timeout.** Wake uses 10 s. Spike C used 500 ms only to keep tests short. Step 12 measures it on staging.
- **How an owner sees a switched-off endpoint** (step 15).
- **The held response.** Settled by [decision 174](../spec/PRODUCT.md#decisions-needed): the agent's accept submits it. Only what the requester sees is left open.
- **`INPUT_REQUIRED` outbound:** which of the agent's text becomes the thread message, within decision 123's limits.
- **The kit's exception list** for the profile, once the kit has run some way.
- **The limits picked here:** 64 KB on a remote response and 256 bytes on a remote task ID.
- **Credential rotation** while both tokens are valid, owed before production.
