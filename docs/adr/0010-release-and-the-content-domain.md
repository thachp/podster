# ADR 0010: Release and the content domain

**Status:** **Proposed** by the architect on 2026-11-12 UTC. Not approved, not independently reviewed, and nothing here is built or bought. It answers what the [M6 plan](../m6-plan.md) and the [architecture](../spec/ARCHITECTURE.md#release-and-deployment-m6) leave "open for the ADR": where content is served and what it can reach, where builds run, credentials, rollback, budgets, takedown and account limits. It rests on [decisions 197 to 211](../spec/PRODUCT.md#m6-decisions-november-12-2026), each decided by the architect for the owner to review, and on working assumptions for the questions only the owner can answer, which are in [the M6 plan's table](../m6-plan.md#for-the-owner). **No spike has run.** An independent review is owed before this is accepted.

## How to read this

Every claim carries one of these labels:

- **Cloudflare's documentation** or **GitHub's documentation:** read on developers.cloudflare.com or docs.github.com on 2026-11-12, said here in this ADR's own words, and linked; the page is the authority. Not run. Where a page was silent it says "not found", and nothing is guessed in its place.
- **Spec:** already in `PRODUCT.md`, `ARCHITECTURE.md` or `ACCESS-CONTROL.md`. Most of those passages are proposals themselves.
- **Proposed:** the architect's proposal in this ADR.
- **Assumed, for the owner:** a working assumption for a question the architect can't answer. If the owner answers otherwise, the section changes.
- **Spike:** not known, and a spike has to find out. [The spikes](#what-stays-open-for-the-spikes) lists each.

Nothing in this ADR is **verified**. No call was made to Cloudflare or to GitHub for it.

## Context

M6 is the first time Podster serves markup and scripts that agents wrote, to anyone on the internet, from infrastructure Podster pays for. Until now every byte Podster served was its own.

- **Spec:** deployed apps "must never share a site with the application". They use a separate registrable domain with a distinct subdomain per room, and "`*.podster.dev` must not host this content" ([content and deployment origins](../spec/ARCHITECTURE.md#content-and-deployment-origins)).
- **Spec:** Workers for Platforms "fits the proposed Podster-hosted default", each room's app a user Worker in an untrusted dispatch namespace "with no bindings to Podster's own data". "Task completion never implies deployment."
- **Spec:** deployment authority is a separate delegation, and "delayed release jobs must recheck relevant authority before … making an external change" ([ACCESS-CONTROL.md](../spec/ACCESS-CONTROL.md#proposed-permission-matrix)).
- **M5** gives a room a managed repository and a merge that Podster made and confirmed, of exactly the reviewed commit ([ADR 0009](0009-managed-repositories.md#the-merge-path)). A release starts from that and from nothing else.

Podster's rules hold throughout: Rust decides authority; a public Worker authenticates or routes and never authorizes; commands and queries are separate, with state, event, outbox and idempotency record in one transaction; read models never authorize; agent content is data; logs carry IDs only.

## Decision

### What a release is

**Proposed** ([decision 197](../spec/PRODUCT.md#m6-decisions-november-12-2026)). A release is a copy of one directory of the room's repository, as it is at one commit, served as static files.

- **The commit** is one that Podster's own merge job put on the default branch and confirmed there. A task branch's head, a commit pushed any other way, and a commit in another repository are never releasable.
- **The directory** has one fixed name, the same in every room. A room can't choose it and the repository can't rename it.
- **Nothing is built.** Podster runs no agent-written build step, and GitHub Actions stay off, as [ADR 0009 proposes](0009-managed-repositories.md#actions-and-workflows). What the agent committed in that directory is what is served.
- **Assumed, for the owner:** static files only, with no agent-written code on the server ([question 5](../m6-plan.md#for-the-owner)). Everything below assumes it. If the owner allows server code, the sections on what content can reach and on budgets must be redone, and Podster would be running code an agent wrote.

### Where content is served

**Proposed.** Three pieces, on a domain used for nothing else.

1. **The content domain,** a separate registrable domain on Cloudflare. Each room's app has one host on it, `<label>.<content domain>`, where the label is generated by the server, is random, and never contains a room's or Podster's name.
2. **A dispatch namespace** in Workers for Platforms, holding one user Worker per room that has a live release. Each holds that release's static files and nothing else.
3. **The content Worker,** a new public Worker (`apps/content`) on the content domain. It is the namespace's dynamic dispatch Worker: it turns a request's host into a user Worker's name, asks the namespace for it, and sets fixed response headers.

What Cloudflare's documentation says of these:

- **Workers in a dispatch namespace are untrusted by default.** In that mode `request.cf` isn't available, each Worker has an isolated cache, and `caches.default` is disabled ([Worker isolation](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/worker-isolation/)). The namespace stays untrusted.
- **A user Worker reaches only the bindings explicitly attached to it** ([bindings](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/bindings/)). No binding is ever attached. Whether a user Worker could reach the account's other Workers some other way: **not found**, and a **spike**.
- **A user Worker in a namespace can carry static assets,** uploaded through the API in three steps: an upload session with a manifest of file hashes, the files themselves, then the script upload naming the completed session ([static assets for user Workers](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/static-assets/)). Whether a user Worker may be assets only, with no script at all: **not found**. If it may not, the script is one fixed file of Podster's that serves nothing itself.
- **Requests served from static assets are free and unlimited** ([billing and limitations](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)). Whether that holds behind a dispatch Worker, which itself runs on every request: **not found**, and a **spike**. The Workers for Platforms pricing page says one request is charged for the whole chain of dispatch Worker, user Worker and outbound Worker.
- **A wildcard route and a wildcard proxied DNS record** put every per-room host on the content Worker: a route pattern whose hostname begins with `*.` matches every subhost, and proxied wildcard records are available on every plan ([routes](https://developers.cloudflare.com/workers/configuration/routing/routes/), [wildcard DNS records](https://developers.cloudflare.com/dns/manage-dns-records/reference/wildcard-dns-records/)).
- **Universal SSL covers the root and first-level subdomains** of a zone on a full setup, and not deeper levels ([limitations](https://developers.cloudflare.com/ssl/edge-certificates/universal-ssl/limitations/)). So per-room hosts are one level deep, and need no certificate of their own. One certificate for all of them also keeps a room's host out of certificate-transparency logs, which a certificate per room would publish.

**The content Worker routes and never authorizes.** It holds no binding to the gateway, the API, D1 or R2, and no secret. It can't tell who is asking and doesn't try: whether a room's app exists to be served is decided by Rust, which is the only thing that uploads to or deletes from the namespace. For a default host, the label is the user Worker's name, so no lookup is needed. Only a custom hostname needs a map from host to name; see [custom domains](#custom-domains).

### What content can reach

**Proposed.**

- **The application.** Nothing. The content domain is another registrable domain, so a page there can't read or set a `podster.dev` cookie. Podster sets no cookie on any content host and accepts no credential there: a request carrying a Podster cookie or an `Authorization` header gets exactly what one without gets ([decision 210](../spec/PRODUCT.md#m6-decisions-november-12-2026)).
- **Podster's data.** Nothing. A user Worker has no bindings, and the content Worker has none to Podster's data.
- **Another room's app.** Its pages, as any site can. Its cookies and storage, **until the content domain is on the Public Suffix List and browsers have shipped it:** before that, one room's app can set a cookie another's reads. The gate doesn't wait for the entry, and nothing security-relevant relies on it. The list's maintainers say they generally decline small projects and experimental or short-term entries ([publicsuffix.org](https://publicsuffix.org/submit/)), so the entry may be refused while Podster is small. This is a recorded gap between rooms' apps, not a gap toward Podster.
- **The network, from the server.** Nothing, because no agent-written code runs there. If the owner allows server code, Cloudflare's documentation offers an outbound Worker that is invoked on every `fetch()` a user Worker makes and that stops it opening TCP sockets with `connect()`, but that doesn't intercept requests made from Durable Objects or through mTLS certificate bindings ([outbound Workers](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/outbound-workers/)). That isn't designed here.
- **The visitor's browser.** Whatever a web page can. The content Worker sets on every response, overriding anything else: `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, a short cache lifetime, and no `Set-Cookie`. It refuses any request but `GET` and `HEAD`, and refuses a request for a service-worker script, so an app can't keep running in a browser after it is unpublished. A sandboxing Content Security Policy is a candidate and a **spike**: it could close the gap between rooms' apps, and could break ordinary apps.

**A finding from the documentation that changes the design.** Cloudflare's static assets honour a `_headers` and a `_redirects` file in the uploaded directory: the limits page gives limits for both, 100 header rules and 2,100 redirects ([limits](https://developers.cloudflare.com/workers/platform/limits/)). Whether they can be switched off: **not found**. An agent could commit either, and so set response headers or redirects on Podster's content domain. So the release job **never uploads a file named `_headers` or `_redirects`**, and the content Worker sets its headers last. Whether user Workers in a namespace honour those files at all is a **spike**.

### Who may open an app

**Assumed, for the owner** ([question 11](../m6-plan.md#for-the-owner)). A public room's app is public. **A private room's app isn't served at all,** because the content Worker can't tell who is asking, and a Podster session on the content domain is exactly what the separate domain exists to prevent. An unguessable address is never the control: addresses leak through browser history and sync, and through certificate-transparency logs for a custom hostname.

A way to serve a private room's app to its own people isn't designed. The candidate is a signed, expiring link that the application issues to someone who can see the room and that the content Worker checks without learning who they are. It needs its own review before it is built, and isn't in M6 unless the owner asks for it.

### The release job

**Proposed.** An outbox job in the room's Durable Object, the only thing that holds the credential that publishes.

1. **Recheck authority,** in the room's transaction, against current state: the requester's deployment grant, the room's `release_config` and its version, the approval the policy needs, that the commit is still one Podster's merge confirmed, and that the room isn't archived or its app suspended (AC-13).
2. **Read the files** from GitHub at that exact commit, with a token for that one repository.
3. **Check them** against the caps, before anything is uploaded.
4. **Upload** to the namespace, under a server-generated name.
5. **Confirm** what is being served, and record the release as live only then. An answer that never came is recorded as uncertain and settled by reading, never assumed (UI-02).

Reading the files, from GitHub's documentation:

- **The Git Trees and Blobs endpoints, not the Contents listing.** the Contents listing stops at 1,000 files for a directory, where a recursive tree holds up to 100,000 entries and 7 MB and a blob up to 100 MB ([contents](https://docs.github.com/en/rest/repos/contents), [trees](https://docs.github.com/en/rest/git/trees), [blobs](https://docs.github.com/en/rest/git/blobs)). A tree whose answer says `truncated` fails the release: the job never publishes part of a directory.
- **Nothing the repository controls is followed.** A tree entry with mode `120000` is a symlink and one with `160000` is a submodule (the modes are listed under "Create a tree" on the same page). Either anywhere in the release directory fails the release. The job reads no configuration from the repository beyond the fixed directory name. Agent content is data.
- **Contents `read` is the one repository permission** those endpoints need, by the [permissions table](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps). That row was read from a summary of a long page and not word for word, so it is a **spike** too. Whether Metadata `read` is also needed: **not found** on the pages read.
- **A token can be cut down** when it is made, to named repositories and to a subset of the App's permissions, never more than the App has. It lives an hour ([installation access tokens](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app)).

**Confirming what is served.** Whether an upload's manifest can be read back through Cloudflare's API: **not found**. So the job doesn't rely on it. It adds one file of its own to every release, at a fixed path, holding the release's ID and commit, and after the upload it fetches that file from the room's host through the content Worker. Live means that fetch returned this release's ID. This also measures how long an upload takes to be served, which is a **spike**.

### Credentials

**Proposed** ([decision 198](../spec/PRODUCT.md#m6-decisions-november-12-2026)). Two, both held by the private API Worker only. The gateway, the web app and the content Worker hold neither.

- **Reading from GitHub: a fourth App,** with Contents `read` and nothing else it can avoid, used by the release job alone. Its token is made for the one repository and never leaves the job. A release borrows none of M5's three Apps: the provisioning App can administer, the agent-token App's tokens go to agents, and the merge App can write the default branch. Creating the App is the **owner's**.
- **Publishing to Cloudflare: one API token.** Here the documentation changes the plan's answer. The plan said the same account would do if the token could be scoped to the namespace. Cloudflare's permissions page lists a "Workers Scripts Edit" permission, giving write access to Workers scripts, in the account category, and **no permission scoped to one dispatch namespace or to Workers for Platforms was found**; nor was the permission the namespace's upload endpoint needs ([API token permissions](https://developers.cloudflare.com/fundamentals/api/reference/permissions/), read in part). If that is the permission, a token that can publish a room's app can also replace Podster's own API Worker. **So the working assumption is now a second Cloudflare account,** holding the content domain, the namespace and the content Worker and nothing of Podster's own, unless a **spike** shows a token that can't touch other Workers. A second account is an account creation, and the **owner's**.

A client never names an account, a namespace, a script or a host label. All four come from trusted configuration or are generated by the server.

### Authority, approval and triggers

**Proposed** ([decisions 199 and 200](../spec/PRODUCT.md#m6-decisions-november-12-2026)).

- **Who configures release:** the room's owner or an admin, as a person, in an Engineering room with a ready repository, and only where the deployment's own configuration allows release at all. An agent never does, whatever its role is called.
- **Who deploys:** the room's owner under the platform's delegation, and anyone the owner gives a `provider_grant` with a `deploy` action. Approval of a task and a merge grant give nothing (AC-17).
- **The approval policy** has two values. `person`: a person with the deployment grant approves each release; the default, and the only value in a public room. `on_merge`: a merge starts the release if whoever asked for the merge also holds the deployment grant, and only in a room that requires a person as reviewer. Under `on_merge` an agent holding both grants publishes with no person acting at that moment; a person chose that, and a person reviewed the work.
- **What starts a release:** a `deploy_release` command, or Podster's own recorded merge under `on_merge`. Never a webhook, and never an observation of GitHub.
- **Decided in `crates/policy` then `crates/core`,** at the command and again in the job.

### Rollback, switching off and removal

**Proposed** ([decisions 203 and 204](../spec/PRODUCT.md#m6-decisions-november-12-2026)).

- **Rollback is a new release** of a commit that was live before, under the same grant and approval. Nothing is rewritten, and each attempt is its own record.
- **A failed release leaves the earlier one serving.** There is no automatic rollback, because there is nothing to roll back from.
- **Switching deployment off, archiving the room, and an operator's suspension each unpublish:** Rust deletes the room's user Worker from the namespace, so the host answers not-found, and the records are kept. The not-found answer carries `Clear-Site-Data`.
- **An owner's departure** leaves the app serving until the room is recovered, as it leaves the repository.

### Custom domains

**Proposed** ([decisions 201 and 207](../spec/PRODUCT.md#m6-decisions-november-12-2026)), on Cloudflare for SaaS custom hostnames. From Cloudflare's documentation:

- **Ownership is validated before traffic is proxied:** Cloudflare verifies the customer's ownership of a hostname before proxying through it. A hostname is `pending` until then and `active` after. Validation is either ahead of time, by a TXT record or an HTTP token, or at the moment the customer adds their DNS record ([hostname validation](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/domain-support/hostname-validation/)).
- **A hostname whose DNS stops pointing at Podster** becomes `moved`, and is deleted after more than seven days in that state ([validation status](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/domain-support/hostname-validation/validation-status/)).
- **A Worker can be the origin** for every custom hostname with one route, `*/*`, and no route per hostname ([Workers as your fallback origin](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/start/advanced-settings/worker-as-origin/)). So custom hostnames reach the content Worker.
- **Pre-validation isn't supported for a hostname whose zone is already on Cloudflare.** A room owner whose own domain is on Cloudflare can only validate at the moment they point it, which the same documentation says may cause some downtime.
- **Whether issuing its certificate publishes the hostname** in certificate-transparency logs: **not found** on the pages read. It is assumed to, as every publicly trusted certificate is.

On top of Cloudflare's validation, Podster keeps its own:

- **One hostname, one room.** A small Durable Object per normalized hostname holds at most one claim, since a D1 row must never authorize. The room commits the request; a job asks the hostname's object; the room commits the claim or the refusal. A job that dies between steps leaves a hostname held and not routed, never held twice.
- **Refused in `crates/core`:** `podster.dev`, the content domain, a subdomain of either, an IP address, and a hostname another room holds.
- **Routing only after both** the room has recorded the claim and Cloudflare reports the hostname `active`. Podster rechecks on a schedule and stops routing when Cloudflare reports `moved`.
- **The map from a custom hostname to a user Worker's name** is the one thing the content Worker looks up. **Proposed:** a Workers KV namespace that the private API writes and the content Worker only reads. It routes; it never authorizes. A wrong or stale entry can serve a room's public app on a hostname, and can't serve anything that isn't already in the namespace.

### Budgets and account limits

**Proposed** ([decision 202](../spec/PRODUCT.md#m6-decisions-november-12-2026)). Podster's own caps, well inside the platform's:

| | Podster's cap, per room | The platform's limit, from Cloudflare's documentation |
| --- | --- | --- |
| Apps | 1 | 1,000 scripts included in the plan, then $0.02 each. The limits page says unlimited, which the pricing page contradicts |
| Files in a release | 1,000 | 100,000 per Worker version on a paid plan |
| Size of a release | 25 MB in all | 25 MiB for one file; no total found |
| Releases a day | 20 | Not found. Cloudflare's API allows 1,200 calls in five minutes for a token |
| Custom hostnames | 1 | 100 included, then $0.10 each, up to 50,000 |

- **What it costs,** from the pricing pages: Workers for Platforms is $25 a month, with 20 million requests and 60 million CPU milliseconds included, then $0.30 a million requests and $0.02 a million CPU milliseconds ([pricing](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/platform/pricing/)). It is bought in the dashboard. Whether it needs Workers Paid first, and how many namespaces an account may have: **not found**.
- **Per-request limits** exist for server code: a dispatch Worker can cap CPU time and the number of subrequests per invocation ([custom limits](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/custom-limits/)). With static files only, the content Worker's own work is the CPU that is billed, and it is the same for every request.
- **Nothing here caps traffic.** A popular or attacked app draws requests Podster pays for past the included 20 million. Cloudflare's own protection applies to the zone; a per-room request cap isn't designed, and whether one is needed is the **owner's**, as money.
- **No cap across rooms.** Each room has its own; nothing adds them up. Before production that is owed, as it is for repositories.

### Takedown

**Proposed** ([decision 205](../spec/PRODUCT.md#m6-decisions-november-12-2026)). Podster hosts this content, so it must be able to stop it without the room's owner.

- **An operator can suspend a room's app and lift that.** Suspension unpublishes, and the room's owner can't switch release back on while it holds. Operators still read nothing private.
- **A report can name a deployed app.**
- **Deployment is off by default,** switched on by a person, and a release is of reviewed, merged code, approved by a person in a public room.
- **What isn't here:** the legal text. Terms, acceptable use and takedown don't yet cover deployed content or custom domains, and `takedown.md`'s staging exception covers public rooms only. Both are the **owner's**.

### Where state lives

**Proposed.** `release_config`, each `release`, the room's hostname request and the outbox jobs are the room's own state, in its Durable Object, through forward-only migrations. They are authority. D1 gets at most a projection for lists, which never authorizes. The hostname's claim is its own Durable Object. The KV map and the namespace are derived: Rust writes both, and either can be rebuilt from the rooms.

### Logs

**Proposed.** Every Worker logs IDs and reason codes only: no token, no file's content or path, no hostname. The content Worker logs nothing per request.

## Alternatives not taken

- **A customer's own Cloudflare account.** Later, with its own delegation design ([decision 11](../spec/PRODUCT.md#decisions-needed) recommends Podster's platform first).
- **Building in GitHub Actions.** It reverses ADR 0009's proposal that Actions stay off, runs agent-written code with a token in the repository, and needs its own decision.
- **A build service of Podster's.** Untrusted code on Podster's account.
- **Serving from R2 behind the content Worker,** with no Workers for Platforms. It would save the add-on. Not proposed: the architecture names Workers for Platforms, a prefix in a bucket isn't an isolation boundary Cloudflare documents, and it has no path to server code later. It is the cheaper fallback if the owner declines the add-on, and would need this ADR's hosting section redone.
- **The merge App's token, cut down to reading.** It puts the merge key in the release path.
- **A unique index in D1 for hostnames.** Simpler, and a read model would be authorizing.
- **A Podster session on the content domain** to gate a private room's app. The separate domain exists to prevent it.
- **A per-room certificate** for default hosts. It would publish every room's host.

## Consequences

- **Podster becomes a host of other parties' content,** with what that brings: abuse, takedown, and a bill that follows traffic.
- **New billed resources,** more than any earlier milestone: a domain, the Workers for Platforms plan, and probably a second account.
- **A fourth GitHub App and a second secret** to keep and rotate.
- **A new public Worker** that must never grow a binding to Podster's data. A test should fail if its configuration gains one.
- **A release is only what was committed.** An app that needs a build step must commit its built files. That is a real limit on "a working web application", and the owner's to accept.
- **Between rooms' apps, cookies aren't isolated** until the Public Suffix List entry ships, and it may be refused.
- **Private rooms get no app** until a way to serve one to its own people is designed.

## What stays open for the spikes

Each needs a resource that doesn't exist yet. [The M6 plan](../m6-plan.md#the-spikes) says which, and what can be learned with none.

1. Whether a user Worker in the namespace can reach anything of the account's without a binding.
2. Whether a user Worker can be assets only, and whether it honours `_headers` and `_redirects`.
3. The narrowest API token that can upload to and delete from the namespace, and whether it can touch other Workers on the account.
4. Whether requests for static assets behind a dispatch Worker are billed, and as what.
5. How long after an upload or a delete the host serves the new state.
6. The custom-hostname flow end to end: that nothing routes before `active`, what happens when DNS moves, and what the customer must publish.
7. Whether a custom hostname can be made to reach another room's app by a `Host` header or SNI.
8. Whether a wildcard route and custom hostnames both reach one Worker on the content zone.
9. That Contents `read` alone reads a tree and its blobs at a commit, for a private and a public repository, and what GitHub answers for a large directory.
10. Whether a sandboxing Content Security Policy closes the gap between rooms' apps without breaking ordinary static apps, and whether refusing service-worker scripts and `Clear-Site-Data` do what this ADR says.

## What an independent review should attack

- **The content Worker.** Can any request make it serve one room's app on another's host, or reach a user Worker Rust didn't intend? Does anything in it, or in its configuration, amount to authorization?
- **The publishing token.** If it is account-wide, what else can it do, and is a second account enough? What stops the release job being steered to another script name?
- **The release job's reads.** Can a repository make it fetch outside the directory, follow a symlink or a submodule, exhaust memory, or publish half a tree?
- **The trigger.** Is there any path from an approval, a merge or a webhook to a release without the deployment grant and the policy? Does `on_merge` let an agent publish where no person reviewed?
- **Stale authority.** A release queued before a grant is taken back, the requester removed, release switched off, or the app suspended.
- **Hostname claims.** Two rooms racing; a claim held after a room is archived; a dangling DNS record pointed at Podster; the gap between Cloudflare's `active` and the room's record.
- **`_headers`, `_redirects` and anything else the platform reads from uploaded files** that this ADR hasn't found.
- **The private-room assumption.** Is "not served at all" really what the design does, including for a room that goes private after a release?
- **What a visitor's browser keeps** after an unpublish or a suspension.
- **Every "not found".** Each is a place where this ADR could be wrong about the platform.

Everything in [the M6 plan's table](../m6-plan.md#for-the-owner). This ADR creates nothing.

## Not verified

Everything. No spike has run, no resource exists, and no call was made to Cloudflare or GitHub. The documentation was read on 2026-11-12 through a page reader, in some cases as a summary of a long page and not word for word: the API token permissions page, the Workers for Platforms API reference, and GitHub's permissions table. Claims that rest on those say so above.
