It covers [M7 Runner](spec/PRODUCT.md#product-direction-and-delivery-scope): "Outbound Runner, CLI adapters, local run policy and budgets". Its gate in that table is R-01 to R-43 of [RUNNER.md](spec/RUNNER.md#proposed-acceptance-criteria-not-executed), including the pairing proof of concept, the automatic-run flow, the server-created repository and local clone, the GitHub access design, a provider and sandbox proof of concept, and a security review of the threat model.

Runner is optional software an agent owner runs on their own machine. Podster never hosts or runs it, and it adds no authority to the server ([ARCHITECTURE.md](spec/ARCHITECTURE.md#podster-runner-m7)). Rust still decides every authorization; Runner is one more client of the gateway, as any Agent Auth agent is.

## The adapter: the owner's ruling of 2026-11-17

**The owner's words, 2026-11-17:** "let's use agent sdk .. but make it adaptable to other agent sdk .. such as openai and grok agent sdk". Later the same day: "no need for claude -p".

This replaces the plan's first choice of adapter, a `claude -p --bare` session of the Claude Code binary, and the owner's follow-up drops `claude -p` from the plan altogether, as a fallback too. The Claude Agent SDK is the only Claude path. Lines that said so are kept below with a dated note rather than rewritten. RUNNER.md's [integration scope](spec/RUNNER.md#purpose-and-direction) already names Claude Code, Codex and Cursor as illustrative, not as a list, and requires that "each integration and mode must be validated separately before support is claimed". Nothing in this ruling changes that, or any of RUNNER.md's rules.

**RUNNER.md now lags this ruling.** Its proposed [Claude Code primary flow](spec/RUNNER.md#local-cli-adapters-and-two-sign-ins) still launches the binary with `-p` and `--bare`, and R-11 still speaks of "Claude bare mode". Both are owed a follow-up RUNNER.md update to the Agent SDK; this change touches only this plan. *Updated 2026-11-17:* RUNNER.md's Claude flow, its budget line, R-11 and its open item now follow the ruling, still Proposed, with the old text struck through and dated.

**The architect's rulings that follow from it, 2026-11-17.** The adapter interface and the first adapter are decided as direction; their details, and every step they touch, stay **Proposed** until the spikes report.

1. **The first adapter drives the Claude Agent SDK,** Anthropic's Python and TypeScript library that runs the Claude Code binary, with its built-in tools, permission control, hooks and sessions. It signs in with the owner's API key only. Unless Anthropic has approved it beforehand, a third-party product, an agent built on the Agent SDK included, may not offer claude.ai login or its rate limits, and is to use API key authentication ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), read by the architect 2026-11-17). So there is no subscription login, as [decision 28](spec/PRODUCT.md#decisions-needed) already says. The terms are rechecked at the gate with the rest of S-31. **There is no CLI fallback.** If spike B shows the SDK can't meet the run policy, that goes back to the owner as a decision. *2026-11-17:* a first draft of this ruling kept `claude -p` as a fallback; the owner's follow-up the same day, "no need for claude -p", removed it before this was recorded.
2. **Runner defines a provider-neutral adapter interface.** The interface, not any SDK, owns:
   - starting a run with the task's prompt marked untrusted;
   - **a decision point for each tool call,** where Runner's run policy allows or refuses it. Runner enforces the tool and network allowlists itself. An SDK's own permission system is a second lock, never the only one;
   - streaming progress, and a final structured result;
   - **budget accounting with a hard stop Runner enforces,** by cancelling the run, alongside whatever the SDK reports about spend;
   - cancellation;
   - **no credential ever passed into the task's container.** Provider keys stay in Runner's broker, outside it.

   Each adapter implements the interface. The run policy, isolation, credentials, budgets and output rules are Runner's, and identical whichever adapter runs.
3. **Later adapters: OpenAI's agent SDK, and an xAI SDK for Grok, if one fits,** named as candidates only. What either offers is not verified here. Each is its own build step after the proof of concept, with its own spike for policy enforcement, budget and isolation, and is validated separately before support is claimed. Both are **Proposed** and outside the proof of concept ([later adapters](#later-adapters)).
4. **Spike B validates the Claude Agent SDK alone** and measures enforcement at each tool call, how far spend overshoots the cap before Runner's hard stop, isolation in the Linux container with the keys outside it, and structured results. **Spike A's language finding must account for the SDKs being Python and TypeScript** ([question 1](#questions)).
5. **Two security-review rows are added:** S-36, a third-party adapter's provider terms and data handling, and S-37, an SDK's permission system treated as defence in depth only ([security review](#security-review)).

### Test machines: the owner's answer of 2026-11-17

**Decided by the owner on 2026-11-17,** answering [question 11](#questions): Runner's test machines against staging are **the owner's own Mac and a second person's machine, Long's, tested together.** So M7's staging acceptance ([step 16](#build-order)) is a two-machine, two-person run:

- **Each person installs Runner on their own machine and pairs it** with their own agent, through step 5's pairing, signed in to staging with their own account. Nothing is installed or paired on the other person's behalf.
- **The run counts only with both people present.** A run with one machine, or with one person driving both, is a rehearsal and is recorded as one, not as the gate's run.
- **Who offers and who reviews comes from the two people,** so a task offered by one person's agent runs on the other's Runner, and the reviewer of a submission is the person who didn't run it. Both directions are run.

This replaces "the owner-approved test machine" and "test agents of test people" for the staging run; local tests still use test people. The test machines' setup (the container of [question 3](#questions), and the provider key of question 5) is each person's on their own machine. Nothing is run yet.

## Spike A results, 2026-11-17

**These are spike results, not decisions.** Everything ran locally: the real gateway source and the API's release build under `wrangler dev` and the Workers test runtime, with no deployment, account, token or provider call. Evidence and method are in [`spikes/m7-agent-auth`](../spikes/m7-agent-auth/README.md). The proposals at the end are for the architect.

1. **Sign-in and reconnect from a machine work** with the client SDK `@auth/agent` 0.6.2 in plain Node, using the M0 claim: the stand-in Runner registered a delegated agent, a person claimed it, and the SDK's own wait ended active, with no browser. A **new process** with only the stored key then called `get_identity` and `read_inbox` as the same Podster agent. A different key under that agent ID was refused. Things to handle: the capability list must be named; the SDK's `disconnectAgent` silently does nothing on the server (`/agent/revoke` is private) while deleting the local copy; its rotate methods are refused; it misreads the gateway's own error shape; and its grant cache can refuse locally after a revocation.
2. **Pairing fits the pinned plugin through its host enrollment,** which Podster doesn't use yet: a signed-in person's `createHost` with no key returns a one-time token (43 characters, 1 hour fixed by the plugin, stored hashed), and the device's `enrollHost` binds its locally generated host key. Agents on that host are active in the plugin at once, but Podster refuses them `agent_unclaimed` until something writes `identity_link`. Today's `/claim` does that for the same person **with any code**, through its retry path, and refuses anyone else. The gaps against RUNNER.md: **no proof of possession** at enrol (any public key is accepted with the token), **re-enrolling an existing key merges it** onto that host, the expiry is fixed at an hour, and there's no fingerprint confirmation. Used, expired and guessed tokens were refused. Smallest set of changes, described and not built: a start route on the person's session that calls `createHost` with no key and Runner's allowlist, with the pairing session in Rust (step 5a); a redeem route that requires a host JWT signed by the submitted key, refuses an already enrolled key, applies the session's shorter expiry and a fail-closed limiter, then calls `enrollHost` server-side; and a confirm step showing the key thumbprint that links through the claim code path. The plugin's approval and key-replacement routes stay private. **The M0 claim works as the fallback,** though it runs the other way (code shown in Runner, entered in Podster).
3. **Keys:** the SDK keeps both private keys as JWKs in whatever storage Runner gives it (the spike used an owner-only file; the SDK has no keychain store). Only public keys and 60-second agent JWTs in the `Authorization` header leave the machine; no private key, JWT or approval code was found in the local Workers' logs. Rotation today is: the owner disconnects, reconnects, and claims a new key onto the same agent with `link_agent_id`, which was shown to keep the agent ID. The owner's disconnect is refused at the Runner's next call (`agent_revoked`); nothing tells a polling Runner sooner. **The claim link carries the approval code in its query string** (`/claim?agent_id=…&code=…`, built by the plugin). Local logs drop query strings, so whether a deployment's logs or traces record it is **not shown**.
4. **Language: TypeScript.** The only Agent Auth client is TypeScript (all three packages in `better-auth/agent-auth`; nothing for the protocol on PyPI, checked 2026-11-17). The Claude Agent SDK has a TypeScript package (`@anthropic-ai/claude-agent-sdk`, not run here). The adapter can run in Runner's process behind the interface; whether isolation wants it in a separate one is spike B's question.

**Proposals for the architect:** question 1, Runner in TypeScript in `apps/runner` with `@auth/agent` pinned exactly; question 2, pairing through host enrollment, so step 5 stays and the owner's fallback isn't needed, with step 5's PRs adding proof of possession on redeem, refusal of an enrolled key, the shorter expiry, and `/claim`'s retry path in its security review; Runner never calls the SDK's disconnect or rotate; and a deployed check of the claim link's query string in request logs, since that's about today's M0 claim, not only Runner. **Not shown:** anything on a deployment, any pairing route (none was built), a real browser, the Claude Agent SDK, OS keychains and isolation.

## Spike B results, 2026-11-18

**These are spike results, not decisions.** Everything ran locally on the owner's Mac: Docker Desktop 28.5.1's Linux VM, `@anthropic-ai/claude-agent-sdk` 0.3.327 for TypeScript pinned exactly, which bundles Claude Code 2.1.327, and `claude-haiku-5-5` on the dedicated key with the owner's 5 USD provider-side limit. No deployment, Podster, Agent Auth key or cloud resource was involved. Evidence and method are in [`spikes/m7-sandbox`](../spikes/m7-sandbox/README.md). The stand-in Runner kept the provider key in a broker on the host (loopback only, `POST /v1/messages` for one model, the key added there); Claude Code got a placeholder and the broker's address. It was tried in two placements: **outside**, Claude Code on the host in an empty folder with every built-in tool removed and Runner's own MCP tools running commands by `docker exec` in a task container with no network; and **inside**, Claude Code's Linux binary in the task container through the SDK's `spawnClaudeCodeProcess`, reaching the broker only through a relay. Task containers ran as an unprivileged user with all capabilities dropped, a read-only root and only their own task folder mounted. The SDK can't meet the run policy alone in two places, (b)'s single request and (c)'s prompt expansion, and Runner closed both itself, so nothing here goes to the owner as a failure.

1. **(a) Enforcement at each tool call: pass.** A `PreToolUse` hook was Runner's decision point. In all four runs (outside and inside, with the SDK set to refuse, `dontAsk` with Runner's allow list, and set open, `bypassPermissions`), each tool call reached the hook before it ran: 3 of 3 each time, built-in `Bash` and `Write` inside, Runner's MCP tools outside. Outside, the evidence that a refused call didn't run is Runner's own tool handler, which logs every execution; inside, where the built-in tools run in Claude Code, it is the files left in `/work` afterwards. A call Runner refused didn't run with the SDK open, and a refusal by Runner alone held where the SDK's list allowed the tool. Controls with Runner allowing everything ran all three calls, so the refusals were what stopped them. The hook returns no opinion on an allowed call, so the SDK's permission system still decides: Runner can only narrow it. Two things to own: **the SDK's structured result is itself a tool call** (`StructuredOutput`) that passes the hook, so Runner's policy must name it; and **one path reaches files with no tool call**: an `@path` in the prompt is expanded by Claude Code. Outside, a host file's contents reached the provider that way; `verbatimPrompts: true` closed it (the SDK documents it also stops slash-command dispatch, not tried). Runner must set it, since task text is the prompt.
2. **(b) Budget: pass, with Runner's stop at the broker.** Against a 0.003 USD cap on a 60-call loop, the SDK's own `maxBudgetUsd` stopped at 0.003089 USD, **2.97% over** (one turn's cost), and Runner's broker stop at 0.003006 USD, **0.19% over** (the request that crossed it); three later requests were refused. No tool ran after Runner's stop; that is measured only for Runner's own stops, which record their time, so for the SDK's stop it isn't shown. The SDK's reported cost matched the broker's count in every run that finished, apart from the probe's own request in one run. **What bounds the overshoot is one request,** and Claude Code asks for `max_tokens` 128000 (about 0.064 USD at Haiku 5.5's list price, far more on larger models). A tool call's input isn't streamed, so neither the SDK nor the broker sees its spend until it ends: in the oversize run below, the model generated for 118 seconds with nothing counted until Runner's time cap cut it, and that spend was never reported. **Runner fixes this at the broker:** it rewrote `max_tokens` to 1024 on every request and refused any request whose worst case (body bytes as input tokens, full `max_tokens` as output) would pass the cap. Spend then never passed the cap; it stopped at 0.0014 USD, 53% under, which is the price of the guarantee.
3. **Decision 29's caps (S-42): pass, enforced by Runner.** **Turns:** the SDK's `maxTurns` 5 and Runner's broker cap of 5 each allowed 5 model requests and 5 tool runs (the SDK reports `num_turns` 6 for the same run); that no tool ran after the stop is measured for Runner's stop only. **Run time:** the SDK has no run-time option, so Runner's timer is the cap. A 15-second cap on a loop of `sleep 3` commands, inside: the stop fired 2 ms after it fell due, Claude Code exited at 106 ms and the container was killed at 188 ms. Runner's stop kills the container, because **killing a `docker exec` client leaves its process running in the container**, which was checked on its own. Spend's overshoot is in result 2. A local stop is the same code path as these stops; it wasn't run with Podster unreachable, since no Podster was involved at all.
4. **(c) Isolation: pass in both placements on this setup.** A probe run as a task command, directly and by the model through Claude Code's Bash tool, found: **no provider key** in its environment, any readable `/proc/*/environ`, the containers' `docker inspect` or anything it printed, only the placeholder; **no home directory** (`/Users` and every path under the owner's home absent); **no other task** (a second task's folder and processes invisible); **network:** outside, none at all; inside, only the relay, with DNS failing, the internet, the Docker host and the host's broker port unreachable, and the broker refusing other paths and models. **Repository content stayed unloaded** with `settingSources: []` and `strictMcpConfig: true`: planted hooks (project and local), an `.mcp.json` server, `CLAUDE.md`, an agent, a skill and `defaultMode: bypassPermissions` all had no effect, and a control run with `settingSources: ["project","local"]` loaded every one of them. Three built-in plugins (`cc-plugin-agents-md`, `cc-plugin-privacy`, `cc-plugin-plugin-authoring`), 16 skills and five built-in agents load whatever the settings; they are part of the pinned binary, not repository content, and the run's tool list had no `Skill` or `Agent` tool to reach them.

   **Where the SDK's process runs: either works; they differ in what a task command shares.** **Outside**, a task command never touches Claude Code, its state or the broker, and the container has no network; but Claude Code runs as the owner's user on the host, so its non-tool paths (the `@path` expansion above) reach host files unless closed, and Runner must provide every task tool itself (shell, read, write, edit, search) as MCP tools executed in the container. **Inside**, Claude Code's own tools work and its host exposure is the container; but a task command runs beside it as the same user: it reads Claude Code's environment (the placeholder, plus a `CLAUDE_CODE_MESSAGING_TOKEN` and socket), its state folder, and can spend through the broker within the run's caps (shown: a probe's own request to the allowed model succeeded). Runner's decision point stays outside in both, since the hook runs in Runner's process over the SDK's stdio.
5. **(d) Structured results: pass.** With `outputFormat` set to a JSON schema, the run ended in a `success` result with an object Runner parsed and bounded (status, a 55-character summary, one file, which existed). Asked for a 3000-character summary into a 200-character field, the run without an output cap hung in one buffered tool call until Runner's time cap and ended with no result, which is recorded as a fail; with a 2048-token cap the SDK's schema check refused the oversize attempts and the run ended with a valid 106-character summary. Error results (`error_max_turns`, `error_max_budget_usd`) arrive as parseable result messages, but the SDK's iterator then throws, and a run Runner cancels yields no result message at all, so Runner records its own outcome.

**Spend: 0.0154 USD counted by the broker** over 28 runs, and up to **0.19 USD more not counted**, from three cut oversize streams (at most 128000 output tokens each). At most 0.21 USD in all, against the 2 USD aim. The owner can confirm it in the Anthropic console. *Corrected 2026-11-18:* this line first said 27 runs; `results/spend.json` lists 28, reruns included.

**Proposals for the architect:** question 3, the supported setup is the **outside** placement: Claude Code in an empty Runner folder with `tools: []`, Runner's own task tools executed in a task container with no network, `settingSources: []`, `strictMcpConfig: true`, `verbatimPrompts: true` and `persistSession: false`, with inside recorded as workable if built-in tools are wanted, its shared-container exposure stated. Step 9's interface takes from this: the decision point is a `PreToolUse` hook that only refuses; the SDK is set to `dontAsk` with Runner's allow list as the second lock; the hard stop for spend and turns lives in the broker, which also clamps `max_tokens` and reserves each request's worst case; run time is Runner's timer; the stop kills the task container; and the result tool is named in the policy. **Not shown:** anything on a Linux host (Docker Desktop's VM was the boundary here), on a deployment or against Podster; the built-in plugins' hooks; whether host Claude Code made other network calls outside (telemetry was switched off by environment, not monitored); tool calls from subagents, slash-command dispatch and parallel tool calls; whether a task command inside can drive Claude Code through its messaging token; Python's SDK; larger models; runs longer than two minutes; and the next SDK or Claude Code version. ### The architect's rulings on spike B, 2026-11-18, for the owner to review

**Decided by the architect on the spike's evidence, under the standing delegation, and open to the owner's review.** Nothing here loosens a security rule, and no code, contract, migration or cloud resource follows from this section alone. Each step it touches stays **Proposed** as a step; what is ruled is its direction. The lines it changes elsewhere in this plan keep their old text, with a dated note. Spike B found no failure for the owner to decide on: where the SDK alone falls short, in (b)'s single request and (c)'s prompt expansion, Runner closes the gap itself. So the owner's question of what follows if the SDK can't meet the run policy ([the adapter](#the-adapter-the-owners-ruling-of-2026-11-17), ruling 1) **does not arise.** These rulings rest on local runs on one Mac, through Docker Desktop's VM, and are rechecked on a Linux host (ruling 6).

1. **Placement: outside. Ruled 2026-11-18.** Claude Code runs on the host, in an empty folder Runner makes for the run, with no built-in tools (`tools: []`). Every task command runs through Runner's own tools (shell, read, write, edit, search), executed in the task's container with no network. **Inside placement is rejected:** a task command there runs beside Claude Code as the same user, so it can read Claude Code's environment and state folder, including its messaging token (`CLAUDE_CODE_MESSAGING_TOKEN`), and spend through the broker ([spike B](#spike-b-results-2026-11-18), result 4). Whether that token lets a task command drive Claude Code wasn't shown, and doesn't need to be: the exposure alone rules inside out. Outside, Claude Code runs as the owner's user on the host, so its non-tool paths are closed by ruling 2. This answers [question 3](#questions) for the Claude adapter. It changes **step 9** and **S-08, S-12 and S-41**.
2. **Settings the Claude adapter always sets, with no way to unset them. Ruled 2026-11-18.** They are fixed in the adapter's code, not read from Runner's configuration, the run policy, the task or anything Podster sends:
   - **`verbatimPrompts: true`,** because Claude Code expands an `@path` in the prompt with no tool call, so Runner's hook never sees it. Outside, a host file reached the provider that way (result 1). Task text is the prompt;
   - **`settingSources: []`,** so no user, project or local settings, hooks, `CLAUDE.md`, agents or skills load from anywhere (result 4);
   - **`strictMcpConfig: true`,** so only Runner's own MCP server loads, never a repository's `.mcp.json` (result 4);
   - **`persistSession: false`,** so nothing of one run is kept for a later one;
   - **the SDK's permission mode is `dontAsk` with Runner's allow list,** as the second lock behind Runner's `PreToolUse` hook, which only refuses (result 1). **`bypassPermissions` is never allowed in Runner,** in any setting or mode, and a repository's `defaultMode` can't set it, since no settings load;
   - **the policy names the `StructuredOutput` tool,** because the SDK's structured result is itself a tool call that passes the hook (result 1). Without it, a run ends with no result.

   This changes **step 9** (b), and **S-04 and S-37**. Step 9's version check (ruling 6) covers what these options mean on the pinned versions.
3. **Budget. Ruled 2026-11-18.**
   - **The hard stop lives in Runner's provider broker, not the SDK.** The SDK's `maxBudgetUsd` and `maxTurns` may be set as well, but never as the only stop (S-37). The broker counts spend and turns from the provider's usage, refuses later requests and cuts those in flight once a cap is reached (result 2);
   - **the broker rewrites `max_tokens` to a bounded value** on every request, and **refuses any request whose worst case would pass the remaining cap,** counting the body's bytes as input tokens and the full `max_tokens` as output. With that, spend never passed the cap in the spike (result 2). The bounded value is a run-policy setting with a fixed ceiling; it can be lowered, not removed;
   - **the broker forwards only to a fixed upstream URL,** built from fixed parts in its own code, with nothing copied from the request: not its host, path or query. It accepts one path for the run's allowed models and adds the key itself;
   - **the broker refuses any request for a model with no entry in its price table,** rather than counting it as zero. *Added 2026-11-18:* spike B's broker priced an unlisted model at 0 USD (`costOf` in `spikes/m7-sandbox/lib/broker.mjs`), so its spend cap would never have fired on one. A model joins the allowed list only with its prices.

   This changes **step 9** (a) and (b), and **S-09 and S-42**.
4. **Run time and stop. Ruled 2026-11-18.**
   - **The run-time cap is Runner's timer,** since the SDK has no run-time option (result 3);
   - **stopping a run kills the task's container,** not only the `docker exec` client, because killing the client leaves its process running in the container (result 3). The same path serves a cap, a cancel, a revocation and the local stop;
   - **Runner records its own outcome** when the SDK's iterator throws after an error result, or a cancelled run yields no result message (result 5). An SDK result, when one arrives, is evidence Runner reads, never the outcome itself.

   This changes **step 8**'s local stop and **step 9** (a), and **S-42 and S-43**. It answers [risk 5](#risks-to-test) for this setup, short of the Linux rerun.
5. **Output bound: every run sets an output-token cap. Ruled 2026-11-18.** Without one, an oversize structured result hung in one buffered tool call until the time cap and ended with nothing; with a 2048-token cap the SDK refused the oversize attempts and the run ended with a valid result (result 5). The cap is a run-policy value with no setting for "none", like decision 29's other caps, and no request may ask for more than it. This changes **steps 7 and 9**, and **S-42**.
6. **Owed to M7's security review. Ruled 2026-11-18.** What spike B didn't show is added to [the security review](#security-review) as new rows:
   - **S-44, the built-in plugins, skills and agents** that load whatever the settings: three plugins, 16 skills and five agents in the pinned binary (result 4). The run's tool list had no `Skill` or `Agent` tool to reach them, but their hooks weren't examined;
   - **S-45, host-side network calls from Claude Code** in the outside placement: telemetry was switched off by environment, but not monitored;
   - **S-46, subagent and parallel tool calls, and slash-command dispatch:** whether each reaches Runner's hook, and whether `verbatimPrompts` stops slash commands, as the SDK documents and the spike didn't try;
   - **S-47, a rerun on a Linux host,** since Docker Desktop's VM was the boundary here. Nothing is claimed for a Linux host until it runs;
   - **S-48, the next SDK version, behind a version check:** Runner pins the SDK and its bundled Claude Code exactly and refuses to run on any other version. A new version is admitted only after spike B's checks pass on it;
   - **S-49, larger models and longer runs,** added 2026-11-18: spike B used only `claude-haiku-5-5` and no run longer than two minutes. Both are rechecked before the gate.

   S-37 and S-42 can cite results 1 to 3, and S-08 and S-41 result 4, for this setup only.

## The owner's decision: decision 29

**This is the owner's, not the architect's.** It loosens a security rule: it removes the per-run check on the owner's machine. **As decided:** ask first for every run from every source, with approval on the owner's machine. Auto-run is opt-in per room, states that it trusts Podster, and is never a global setting for public rooms.

**As proposed on 2026-11-08:** eligible tasks run automatically within owner-configured access and limits, without per-run approval. Out-of-scope work doesn't start. Public rooms need explicit per-room configuration and a trust warning. A manual mode stays available.

## Risks to test

1. **Agent Auth from a machine:** whether the pinned `@better-auth/agent-auth` 0.6.2 supports a non-browser client's sign-in and reconnect by key, and a Podster-started pairing, without its private routes. Spike A. *Note, 2026-11-17:* answered locally, yes for both ([spike A results](#spike-a-results-2026-11-17)); not shown on a deployment.
2. **The credential conflict:** whether any setup keeps the provider key from commands the CLI runs for the task. If none does, the adapter is unsupported. Spike B. *Note, 2026-11-18:* answered locally: the outside placement keeps the key in Runner's broker, out of every task command's reach ([the architect's rulings on spike B](#the-architects-rulings-on-spike-b-2026-11-18-for-the-owner-to-review), ruling 1); a Linux host is S-47.
3. ~~**`--bare`:** whether it loads nothing from the repository on the pinned Claude Code version, and whether the next version changes that.~~ *Superseded 2026-11-17 by the owner's follow-up, "no need for claude -p":* **Repository settings under the Agent SDK:** whether the SDK, as configured, loads nothing from the repository on the pinned SDK and Claude Code versions, and whether the next version changes that. *Note, 2026-11-18:* on the pinned versions, `settingSources: []` and `strictMcpConfig: true` load nothing from the repository; the next version is S-48, and the built-in plugins, skills and agents are S-44 ([the architect's rulings on spike B](#the-architects-rulings-on-spike-b-2026-11-18-for-the-owner-to-review)).
4. ~~**Budget overshoot:** how far spend passes `--max-budget-usd` and Runner's own total.~~ *Superseded 2026-11-17 by the owner's follow-up, "no need for claude -p":* **Budget overshoot:** how far spend passes the cap before Runner's hard stop cancels the run, beside what the SDK reports. *Note, 2026-11-18:* one request bounds it; with the broker's `max_tokens` rewrite and worst-case refusal, spend didn't pass the cap at all ([the architect's rulings on spike B](#the-architects-rulings-on-spike-b-2026-11-18-for-the-owner-to-review), ruling 3).
5. **Process trees:** whether cancel stops every descendant inside the container, and what is reported when it doesn't. *Note, 2026-11-18:* killing a `docker exec` client doesn't; killing the task's container does, and Runner records its own outcome ([the architect's rulings on spike B](#the-architects-rulings-on-spike-b-2026-11-18-for-the-owner-to-review), ruling 4).
6. **Lost answers:** a lost `accept_task` or `submit_task` answer, retried with the same key, gives one outcome and one run.
7. **Canceled after accept:** a retried accept that returns a stored success after a cancel; the fresh read must catch it.
8. **Least-trusted author:** a reviewer from outside the configured scope writes a change request; the rerun must not start automatically.
9. **The broker:** whether a credential helper can serve Git without exposing the token to a task command that reads the helper's socket or files.
10. **Off-default-branch writes:** whether the CLI, through the broker, can push to another task's branch (S-21).
11. **Pull request text as output:** a public managed repository publishes a task branch before review (decision 181).
12. **Offline and restart:** an offer made while Runner is down is found after reconnect; a run interrupted by a restart resumes only if the process and inputs match.
13. **Logs:** no code, key, token, task text or hostname in Runner's logs or support bundles.
14. **Hostile Podster:** forged allowed labels trigger automatic runs within limits, and nothing more (R-21).
15. **The nudge:** a forged, replayed or oversized request to the endpoint changes nothing and starts nothing, and a missed nudge loses no work because polling finds it (R-03, R-16).
16. **Runner's lock alone:** added 2026-11-17. With an SDK's own permission system set open, a tool call Runner's policy refuses still doesn't run (S-37). Spike B, and each later adapter's spike.
17. **An adapter that misbehaves:** added 2026-11-17. An adapter that ignores a refusal, under-reports spend or passes a credential through is caught by the interface, not trusted. Step 9's fake adapters.
18. **Stopping at once:** added 2026-11-17 by [the owner's ruling](#the-owners-ruling-on-decision-29-2026-11-17). A local stop ends the run and every descendant with Podster unreachable; a task that hits its turn or run-time cap stops there; and nothing from Podster switches unattended runs on (S-40 to S-43).
